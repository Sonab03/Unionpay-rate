# 日元消费汇总功能设计

日期：2026-09-02

## 目标

在现有银联日元汇率网站中新增 `/expenses` 页面，让用户按消费日期记录日元支出。系统使用该日期对应的银联 JPY/CNY 汇率计算每笔支出的人民币金额，并汇总累计 JPY、累计折合 CNY、加权平均汇率及平均每 10,000 JPY 对应的 CNY。

消费记录仅保存在当前浏览器，不需要账号或登录。用户可以下载 JSON 存档，也可以在以后加载存档并继续使用。

## 非目标

- 第一版不在服务器保存消费记录。
- 第一版不提供账号、跨设备同步或多人共享。
- 第一版不支持其他货币或其他汇率来源。
- 第一版不把消费记录上传到服务器。
- 第一版不提供 CSV、Excel、图表或消费分类统计。

## 页面与导航

首页增加“消费汇总”入口，链接到 `/expenses`。消费页提供返回当前汇率页的入口，并复用现有深浅色主题、颜色变量、卡片样式和移动端布局。

消费页由四部分组成：

1. 汇总区：累计消费 JPY、累计折合 CNY、加权平均的 `1 JPY = x CNY`，以及 `平均 10,000 JPY = x CNY`。
2. 记录表单：消费日期、JPY 金额和可选备注。日期默认今天。
3. 明细区：显示消费日期、实际汇率日期、汇率、JPY、折合 CNY 和备注，并提供编辑和删除操作。
4. 存档区：下载 JSON 存档和加载 JSON 存档。

没有记录时显示简短说明，不显示没有意义的零值平均汇率。

## 总体结构

采用“服务器提供历史汇率，浏览器保存消费记录”的混合结构：

- FastAPI 提供 `/expenses` 页面。
- FastAPI 提供 `GET /api/rate?date=YYYY-MM-DD` 历史汇率接口。
- 服务器复用现有 UnionPay 请求、校验和 `data/history/` 缓存机制。
- 浏览器 JavaScript 负责记录的新增、编辑、删除、汇总、本地保存及 JSON 导入导出。
- 任何消费记录、备注和汇总结果都不发送到服务器；服务器只接收所查询的日期。

## 历史汇率查询

接口接收 ISO 日期 `YYYY-MM-DD`，只允许合法且不晚于日本时区当天的日期。

查询顺序如下：

1. 从请求日期开始检查服务器历史缓存。
2. 缓存没有该日数据时，请求银联该日 JSON。
3. 如果银联明确表示该日没有数据，则向前检查一天。
4. 最多向前寻找 14 天，找到第一条有效 JPY/CNY 汇率即停止。
5. 成功取得的汇率写入现有 `data/history/YYYY-MM-DD.json`。
6. 将请求日期到实际汇率日期的成功映射持久化到 `data/date-lookups/YYYY-MM-DD.json`，避免周末和节假日重复请求不存在的日期。

同一时间的历史查询使用文件锁串行处理，锁内再次检查缓存，避免并发请求重复访问银联。每次查询最多访问 14 个日期，使外部请求范围有明确上限。

成功响应格式：

```json
{
  "requestedDate": "2026-08-30",
  "rateDate": "2026-08-28",
  "rate": 0.042334,
  "source": "UnionPay International"
}
```

错误规则：

- 日期格式错误或未来日期：HTTP 400。
- 14 天内没有有效数据：HTTP 404。
- 银联超时、拒绝请求或返回异常内容：HTTP 502。

接口不能用更早的缓存汇率掩盖银联通信错误。只有银联明确返回“该日无数据”时才继续向前寻找。

## 浏览器记录模型

本地存储键固定为 `unionpay-expenses-v1`。值是以下结构：

```json
{
  "schemaVersion": 1,
  "records": [
    {
      "id": "0b0d80ea-12d7-4b71-b9c0-e0b56b280e57",
      "purchaseDate": "2026-08-30",
      "jpyAmount": 12000,
      "note": "交通",
      "rateDate": "2026-08-28",
      "rate": 0.042334,
      "createdAt": "2026-09-02T01:00:00.000Z",
      "updatedAt": "2026-09-02T01:00:00.000Z"
    }
  ]
}
```

`id` 使用浏览器生成的 UUID。备注最长 200 个字符。JPY 金额必须是有限且大于零的数字。日期必须是有效 ISO 日期，且实际汇率日期不能晚于消费日期。汇率必须是有限且大于零的数字。

CNY 金额不重复保存，始终由 `jpyAmount × rate` 计算。这样可以避免存档中出现互相矛盾的金额和汇率。

## 新增、编辑与删除

新增记录时：

1. 浏览器验证日期和金额。
2. 调用历史汇率接口。
3. 成功后创建完整记录并写入 localStorage。
4. 更新汇总和明细。

如果汇率查询失败，不写入不完整记录，保留用户已输入的内容并显示可重试错误。

编辑记录时，表单载入现有值。只修改备注时可以沿用原汇率；修改消费日期或 JPY 金额时重新验证，其中日期变化必须重新查询汇率。保存编辑时保留 `id` 和 `createdAt`，更新 `updatedAt`。

删除记录前显示确认提示。确认后删除并立即更新本地存储和汇总。

## 汇总计算

对所有有效记录计算：

```text
totalJPY = Σ jpyAmount
totalCNY = Σ (jpyAmount × rate)
weightedAverageRate = totalCNY ÷ totalJPY
averagePer10000JPY = weightedAverageRate × 10000
```

加权平均按消费金额计算，不对每天的汇率做简单算术平均。页面内部使用完整数值计算，仅在展示时格式化：JPY 不强制小数，CNY 显示两位小数，平均汇率显示六位小数，每 10,000 JPY 的平均值显示三位小数。

## JSON 存档

下载文件名为 `unionpay-expenses-YYYY-MM-DD.json`，格式如下：

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-09-02T01:00:00.000Z",
  "records": []
}
```

导出文件包含完整记录及当时使用的汇率快照，因此加载存档时不重新请求银联，恢复结果与导出时一致。

导入流程：

1. 限制文件为 JSON，文件不超过 5 MiB，记录不超过 10,000 条。
2. 解析后验证顶层结构、版本和每条记录的全部字段。
3. 在内存中完成全部验证；任意一条异常都拒绝整个文件，localStorage 保持不变。
4. 按记录 `id` 与当前记录合并。
5. ID 不同的记录全部保留；ID 相同且内容不同的记录保留 `updatedAt` 较新的版本；时间相同时保留当前浏览器版本。
6. 完成合并后一次性写入 localStorage 并重新计算。

重复加载同一存档不会产生重复消费记录。

## 错误处理

- localStorage 数据损坏时不自动覆盖原始值；页面显示恢复提示，并允许用户加载有效存档。
- localStorage 空间不足或写入失败时，界面显示错误且不假装保存成功。
- JSON 导入失败时显示具体但不泄露内部信息的错误，例如格式无效、版本不支持或记录字段异常。
- 历史汇率请求期间禁用提交按钮，避免重复提交。
- 网络失败时保留表单输入，允许用户重试。
- 服务器日志记录上游错误类别，但不记录消费金额或备注。

## 测试策略

服务器端测试覆盖：

- 精确日期缓存命中。
- 指定日期无数据后向前找到最近有效汇率。
- 最多回溯 14 天。
- 未来日期和无效日期被拒绝。
- 银联异常返回 502，而不是误用旧汇率。
- 并发查询通过锁和二次缓存检查避免重复请求。
- `/expenses` 页面和首页入口可访问。

浏览器逻辑应拆分为可独立测试的纯函数，测试覆盖：

- 单条及多条消费的 CNY 计算和加权平均。
- 金额较大的记录具有相应权重，而不是简单平均汇率。
- 新增、编辑、删除后的记录状态。
- 日期变化触发汇率更新，备注变化保留汇率。
- 导出结构和版本。
- 导入完整验证、原子失败、按 ID 去重及按 `updatedAt` 合并。
- 损坏的 localStorage 数据不会被静默覆盖。

最终验证包括完整自动化测试、临时服务 HTTP 检查、移动端宽度检查、深浅色主题检查，以及部署后的公网页面和服务状态检查。

## 发布与兼容性

现有 `/` 和 `/refresh` 行为保持兼容。新功能不迁移现有服务器数据，也不改变当前汇率缓存格式。版本号在功能上线时递增。

第一版 localStorage 使用 `schemaVersion: 1`。未来改变记录结构时必须新增显式迁移或拒绝不支持的版本，不能静默猜测字段。
